## 3. 대표 시나리오 검증 기록

각 시나리오는 `python -m scripts.run_scenarios [번호]` 로 실제 실행하면 `docs/evidence/scenario_N.md`(답변·조건·Tool 표·이벤트 표·원본 JSON)와 `summary.md`가 생깁니다. 아래 “결과” 칸은 실행 후 채웁니다.

| # | 유형 | 요청 | 기대 동작 | 증거 파일 | 결과 |
|---|---|---|---|---|---|
| 1 | 한 번에 충족 | 부산, 날짜·시간대 지정, 초보 | 재계획 0회, 추천 1건 이상 | `evidence/scenario_1.md` | ⬜ |
| 2 | 재계획 필요 | 양양 요청 → 조건 불충족 → 인접 지역 확장, 이어서 “포항은?” | 재계획 ≥1, 지역 확장 사실을 답변에 밝힘, 후속 요청은 캐시 재사용 | `evidence/scenario_2.md` | ⬜ (유사 사례 ✅ 아래 4절) |
| 3 | 재계획 상한 도달 | 기준값을 일시적으로 극단값(0.05 m / 0.1 m/s)으로 바꿔 어떤 스팟도 통과 못 하게 함 | 재계획 3회에서 멈추고 “찾지 못했다” 안내 | `evidence/scenario_3.md` | ⬜ |
| 4 | Tool 하나 실패 | 카카오 키를 비운 상태에서 서핑샵 요청 | 추천은 유지, “서핑샵 정보는 불러오지 못했어요” | `evidence/scenario_4.md` | ⬜ |
| 5 | Tool 불필요 | “안녕! 이 서비스는 뭘 할 수 있어?” | Tool 호출 0회, 안내 답변 | `evidence/scenario_5.md` | ⬜ |

시나리오 3은 설정값을 임시로 바꾸고 `finally`에서 원복합니다. 같은 6개 요청은 자동 테스트(🧪 `test_graph.py`)로도 흐름을 확인했습니다.

각 `scenario_N.md` 끝에는 **“차이” 칸**이 있습니다. 기대와 실제가 다르면 숨기지 말고 거기에 적어 주세요.

## 4. 대표 요청 1건 전체 실행 로그 / 재계획 사례

아래는 **실제 외부 API와 LLM으로 실행한** `scripts/chat_cli.py` 기록입니다(2026-11-19). 이 실행 이후 `effective_end` 수정이 들어갔기 때문에 “수정 전” 결과임을 밝혀 둡니다(발견 경위는 요구사항 정의서 4-3).

### 4-1. 요청

> 토요일 오전에 양양에서 초보가 탈 만한 곳 찾아줘, 오후 2시 전엔 나와야 해

### 4-2. 최종 답변 (발췌)

```
2026-11-21 06:00~12:00 · 초보 기준으로 확인한 결과예요.
요청하신 양양은(는) 조건에 맞지 않아 포항, 부산까지 넓혀 확인했어요.

추천
1. 부산 송정 — 적합 (최대 파고 0.40m, 최대 풍속 4.5m/s)
2. 부산 해운대 — 주의 (최대 파고 0.28m, 최대 풍속 4.7m/s) - 파고 0.28m로 파도가 약함

14:00까지 끝내려면 늦어도 12:00에는 시작해야 해요(서핑 2시간 기준).

제외한 곳
- 양양 죽도·인구·기사문: 파고 0.90m > 0.8m, 풍속 8.2~8.7m/s > 5.0m/s
- 포항 월포·용한: 파고 0.98m > 0.8m, 풍속 6.5~7.1m/s > 5.0m/s
```

### 4-3. 실행 기록 (재계획 2회)

```
의도: plan_request
조건: date 2026-11-21, start_time 06:00, end_time 12:00, region 양양, level 초보, end_by 14:00
시도한 지역: 양양 → 포항 → 부산 (재계획 2회)
 1. [OK] get_wave_forecast   (재계획 0회차, 1128ms)
 2. [OK] get_beach_weather   (재계획 0회차, 3204ms)
 3. [OK] get_wave_forecast   (재계획 1회차, 1097ms)
 4. [OK] get_beach_weather   (재계획 1회차, 2127ms)
 5. [OK] get_wave_forecast   (재계획 2회차, 1096ms)
 6. [OK] get_beach_weather   (재계획 2회차, 2116ms)
```

→ 3개 지역 확인에 Tool 시간 합계 약 10.8초(순차 호출). NF3005의 근거입니다.

### 4-4. 이벤트 흐름 (재계획 1회째까지, 실제 `/log` 출력)

```
#1 step_start analyze → #2 step_end analyze → #3,#4 plan → #5 work 시작
#6 tool_request get_wave_forecast → #7 tool_response → #8 tool_request get_beach_weather → #9 tool_response → #10 work 끝
#11 judge 시작 → #12 judge_result → #13 judge 끝
#14 replan 시작 → #15 replan(포항) → #16 replan 끝 → #17 work 시작 …
(부산까지 반복 후) #38 respond 시작 → #39 respond 끝
```
요청 3개 후 세션 이벤트는 총 85개가 저장되었습니다.

### 4-5. 같은 세션의 후속 요청 (맥락·캐시 사용)

| 요청 | 의도 | 결과 |
|---|---|---|
| “포항은?” | `modify_request` — **지역만** 포항으로 바뀌고 날짜·시간·종료 제한은 유지 | Tool 4건 모두 **캐시**(0ms)로 처리, 같은 추천 |
| “서핑하고 싶어” | `plan_request` — 조건 유지(포항 시작) | 역시 캐시로 처리 |

### 4-6. 이 기록에서 확인한 것 / 못 한 것

| 확인한 것 | 못 한 것·한계 |
|---|---|
| 재계획 2회, 지역 확장 사실이 답변에 포함됨 | 이 실행은 파고 결과를 해변 날씨에 직접 전달하도록 고치기(`chain_beach_args`) **전**의 기록 |
| 제외 이유가 수치와 함께 표시됨 | 판정 시간대가 06~12시에서 끝났음(종료 제한 14시까지 보도록 `effective_end`로 **수정함**) |
| 후속 요청에서 캐시 재사용 | 수정 후 같은 요청의 재실행 결과 ⬜ (시나리오 2 실행으로 대체 가능) |
