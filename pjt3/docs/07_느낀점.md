# 7. 느낀점

> 초안입니다. 프로젝트를 진행하며 있었던 일(대화 기록)을 바탕으로 썼으니, 실제로 느낀 것과 다른 부분은 고쳐서 제출하세요.

## 한 줄 소감

“LLM에게 다 맡기는 것”이 Agent가 아니라, **어디까지 LLM에게 맡기고 어디부터 코드로 책임질지 정하는 일**이 Agent 설계라는 걸 배웠습니다.

## 1. 가장 크게 배운 것

**LLM은 한 곳에만 쓰고, 숫자는 코드가 책임지게 했습니다.** 요청 분석(analyze)에서만 LLM을 쓰고, 파고·풍속 판정과 답변 문장은 규칙으로 만들었습니다. 처음에는 LLM이 답변까지 써 주면 더 자연스러울 거라고 생각했지만, 서핑 가능 여부처럼 안전과 연결된 숫자가 바뀔 수 있다는 점이 마음에 걸렸습니다. 그래서 LLM이 준 값도 코드가 형식을 다시 검증하고(잘못된 값은 버림), “사용자가 말하지 않은 시각은 채우지 않는다”를 프롬프트와 코드 양쪽에 넣었습니다.

**“한 번에 모든 걸 만드는 것”보다 “한 기능씩 만들고 확인하는 것”이 훨씬 빨랐습니다.** 비전공자로서 처음부터 큰 그림을 한 번에 짜는 건 어려웠지만, Tool → 판정 → 상태 → 로깅 → 노드 → 그래프 → 저장 → API → 화면 순서로 하나씩 만들고 테스트를 붙이니 막혔을 때 어디가 문제인지 바로 알 수 있었습니다.

## 2. 어려웠던 점과 해결

| 어려웠던 일 | 어떻게 풀었나 |
|---|---|
| 외부 API 응답이 예상과 달랐다 — 기상청은 풍속이 아니라 동서·남북 성분(UUU, VVV)만 주고, ±900은 결측값이었다 | 풍속을 직접 계산하고 결측을 `None`으로 처리했다 |
| 해변 번호 대응이 틀렸다(1번이 서핑 스팟이 아니라 을왕리) | 번호를 하나씩 호출해서 이름을 확인하고 스팟 목록을 고쳤다 |
| 카카오 앱 활성화·카카오맵 사용 설정 때문에 호출이 안 됐다. 쿼터 초과가 429가 아니라 400(코드 -10)으로 오기도 한다는 것도 나중에 알았다 | 설정을 확인해 해결하고, 쿼터 오류를 `RATE_LIMITED`로 매핑하는 테스트를 추가했다 |
| 파고 예보가 정확히 맞는지 확신할 수 없었다 | 오늘 날짜는 실측과 비교해 0.5 m 이상 차이 나면 “예보 신뢰도 낮음, 현장 확인 필요”로 경고하게 했다 |
| 기준 수치(초보 0.3~0.8 m, 5 m/s)를 어떻게 정할지 정답이 없었다 | 근거와 한계를 문서에 적고 `config.py`에서 바꿀 수 있게 했다 (전문가 검증을 받은 값은 아니다) |

## 3. 실제로 돌려 보고 나서 알게 된 것

자동 테스트가 모두 통과해도 **실제 요청 한 번**이 문제를 드러냈습니다. “오후 2시 전엔 나와야 해”를 말했는데 판정 시간대가 12시에서 끝나고 있었습니다. 테스트는 가짜 데이터라 통과했지만 실제 흐름에서 어긋난 것을 보고 `effective_end`로 고쳤습니다. 문서를 쓰면서도 비슷한 일이 있었습니다. 파고 Tool이 고른 후보 스팟이 해변 날씨 Tool에 그대로 넘어가지 않고 계획의 목록이 쓰이고 있다는 것을 설계 문서를 정리하다가 알아채고 `chain_beach_args`로 고쳤습니다. **문서를 코드와 대조해서 쓰는 일 자체가 검증이 된다**는 걸 느꼈습니다.

## 4. 재계획을 만들면서

“후보가 없으면 날짜를 바꿔서라도 찾아 주는” Agent는 편해 보이지만 사용자가 원한 조건을 몰래 바꾸는 것이라서 **날짜·시간은 절대 바꾸지 않고 지역만 넓히고, 넓혔다는 사실을 답변에 밝히는** 규칙으로 정했습니다. 상한(3회)이 없으면 같은 실패가 계속 이어질 수 있다는 것도 설계하면서 실감했습니다. Tool 결과를 캐시로 재사용하니 “포항은?” 같은 후속 질문이 즉시 처리되는 것도 직접 확인했습니다.

## 5. 아쉬운 점 (솔직하게)

- 심화(F3020~F3023)는 시간 관계상 선택하지 않았습니다.
- 스팟은 9곳 고정 목록이고, 판단 기준은 초보만 있습니다. 해변 방향(온쇼어/오프쇼어)도 반영하지 못했습니다.
- Tool 선택이 규칙 기반이라 “LLM이 필요한 Tool을 고르는” 구조까지는 가지 못했습니다.
- 3개 지역 확인에 약 10초가 걸립니다. Tool을 순차 호출하기 때문이며 병렬화하면 줄일 수 있습니다.
- `llm_decision` 이벤트를 정의만 해 두고 쓰지 않았습니다.
- 실제 데이터로 찍은 화면 증거는 마지막에 직접 채워야 합니다.

## 6. 다음에 해 보고 싶은 것

- Planner와 Worker를 나누는 심화 구조, 병렬 Tool 호출
- 중급·상급 기준과 해변 방향(바람 방향)을 반영한 판정
- 스팟 목록을 코드에 고정하지 않고 검색으로 넓히기
- 이번에 만든 시나리오 실행 스크립트를 회귀 테스트처럼 계속 쓰기

## 7. 마무리

비전공자로서 Agent, Tool, 상태, 로깅이 서로 어떻게 연결되는지 직접 만들며 이해할 수 있었습니다. 특히 **“동작한다”와 “검증했다”는 다르다**는 것, 그리고 **되는 척하지 않고 한계를 문서에 적는 것**이 결과물의 신뢰도를 높인다는 것을 이번 프로젝트에서 가장 크게 배웠습니다.
