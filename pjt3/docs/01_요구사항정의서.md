## 2. 기능별 요구사항 상세

| ID | 입력 | 처리 | 출력 | 완료 기준 |
|---|---|---|---|---|
| F3001 | Tool 이름·인자 | 레지스트리에서 함수 실행 | `{"ok":true,"data":…}` 또는 `{"ok":false,"error":{code,message}}` | 모든 Tool이 같은 형식으로 응답, 예외는 `UNKNOWN`으로 변환 |
| F3002 | region, date, (start/end) | Open-Meteo Marine 호출 → 후보 스팟별 최대 파고 | 스팟별 `max_wave_height_m` | 날짜 누락/형식 오류 → `INVALID_INPUT` |
| F3003 | spot_ids, date, (start/end) | 기상청 3개 오퍼레이션 호출, 풍속=√(UUU²+VVV²), ±900은 결측 | 스팟별 시간대 예보, 최대 풍속, (오늘) 실측 | 일부 스팟 실패해도 나머지 반환 |
| F3004 | spot_id, category, size | Kakao 키워드 검색(반경 5km, 거리순) | 장소명·주소·전화·거리 | 결과 없음 → `NO_DATA` |
| F3005 | 사용자 메시지 | 조건 병합(바뀐 항목만 갱신), 최근 6턴 보관 | 갱신된 상태 | 날짜가 바뀌면 Tool 캐시 비움 |
| F3006 | 메시지 + 현재 조건 | LLM이 JSON 출력, 코드가 검증(잘못된 값은 버림) | intent, reason, conditions | 말하지 않은 조건은 `null` |
| F3007 | 조건 | 파고·해변 날씨 작업 생성, 시각은 사용자가 말한 것만 | task_queue | 날짜 없으면 되묻기(`need_info`) |
| F3008 | task_queue | 순차 실행, 캐시 재사용, 오류 코드별 분기 | tool_log, tool_cache | `NON_RETRYABLE`은 즉시 중단, `RETRY_ONCE`는 같은 인자로 1회 |
| F3009 | Tool 요약 | 기준표로 적합/주의/부적합/판정 불가 | 후보·제외 목록 | `LEVEL_LIMITS["초보"]` 적용 |
| F3010 | 후보 0개 | 가까운 지역 순으로 재계획(최대 3회) | 새 task_queue | 날짜·시각 조건은 바꾸지 않고, 지역 확장을 답변에 밝힘 |
| F3011 | 판정 결과 | 규칙 기반 문장 생성 | 답변 텍스트 | 출처·면책 항상 포함 |
| F3012 | 이벤트 | 버스 → 구독자 | – | collector 없이도 그래프 실행 |
| F3013 | – | 단계마다 emit | `event_log` 행 | 세션 내 `seq` 순서 보장 |
| F3014 | session_id | 조회/삭제 | 이벤트 목록 | 수정 API 없음 |
| F3015 | “2번 저장해 줘” | `last`의 후보에서 선택 | plans 행 | 선택 불가 시 되묻기 |
| F3016 | plan_id, 수정값 | 수정 후 겹침 검사 | 계획 + overlaps | 겹쳐도 수정은 반영하고 경고만 |
| F3017 | HTTP 요청 | FastAPI | JSON | `/docs` 자동 문서 |
| F3018 | 사용자 조작 | fetch로 API 호출 | 화면 | 3개 탭 동작 |
| F3019 | 키 누락 | `MISSING_KEY` → `error` 필드 | 안내 문구 | 키 이름과 넣을 위치를 알려줌 |

## 3. 도메인 선택과 조건 충족 근거

### 3-1. 외부 API 목록

| API | 키 | 용도 | 비고 |
|---|---|---|---|
| Open-Meteo Marine | 불필요 | 파고 예보 | 비상업, CC BY 4.0 |
| 기상청 전국 해수욕장 날씨 | 필요 | 풍속·풍향·기온·강수·실측 파고/수온 | `getVilageFcstBeach`, `getWhBuoyBeach`, `getTwBuoyBeach` |
| Kakao Local 키워드 검색 | 필요 | 서핑샵·숙소·맛집 | 반경 5km |
| LLM (GMS, OpenAI 호환) | 필요 | 요청 분석 한 곳 | |

### 3-2. 제약 있는 요청 예시

| # | 요청 | 제약 | 판단에 쓰는 Tool |
|---|---|---|---|
| 1 | “이번 주 토요일 오전, 초보인데 부산에서 서핑할 수 있어?” | 날짜·시간대·실력 | 파고 + 해변 날씨 |
| 2 | “내일 양양에서 서핑, 점심 전에는 나와야 해” | 날짜·종료 제한 | 파고 + 해변 날씨 |
| 3 | “이번 주말 서핑 괜찮은 곳 추천해줘. 근처 맛집도” | 날짜 + 장소 정보 | 파고 + 해변 날씨 + 장소 검색 |
| 4 | “포항은?” (후속) | 지역만 변경, 나머지 유지 | 같은 날짜 조건으로 재조회 |

### 3-3. 저장할 결과물

- **서핑 계획**: 스팟, 날짜, 시작·종료 시각, 메모 → `plans` 테이블(`GET/PATCH/DELETE /api/plans`)
- **실행 로그**: 요청 단위 이벤트 기록 → `event_log` 테이블(`GET/DELETE /api/logs`)

## 4. 기획 검증 결과

> 이 절은 **구현 전에 확인한 사항과 그 때문에 바뀐 설계**입니다.

### 4-1. API 호출 확인

| 항목 | 방법 | 결과 |
|---|---|---|
| Open-Meteo Marine | 지역별 좌표로 실제 호출 | ✅ 후보 스팟별 파고 수신 (`scripts/check_tools.py`) |
| 기상청 해수욕장 3종 | 해변 번호로 실제 호출 | ✅ 수신. 단, 해변 번호 대응을 점검해 **`beach_num=1`이 을왕리**임을 발견하고 스팟 번호를 새로 확인 |
| Kakao 키워드 검색 | 스팟 좌표·반경으로 실제 호출 | ✅ 수신. 앱 활성화·카카오맵 사용 설정 이슈를 거쳐 호출 성공 |
| 실제 대화 1회 | `scripts/chat_cli.py` | ✅ 실제 요청 1건 실행(아래 4-3 개선 사례 참고) |

### 4-2. Tool 출력 구조 대조

| 확인 사항 | 결과 | 반영 |
|---|---|---|
| 기상청 풍속 | 풍속 필드가 없고 동서(UUU)·남북(VVV) 성분만 제공 | 풍속 = √(UUU²+VVV²)로 계산 |
| 결측값 | ±900 이상은 결측 | `_num()`에서 `None` 처리 |
| 실측 파고·수온 | 현재 시점 값만 제공 | **오늘 날짜일 때만** 조회, 그 외는 `None` 명시 |
| Kakao 쿼터 초과 | HTTP 429가 아니라 **400 + 에러 코드 -10**으로 오기도 함 | `RATE_LIMITED`로 매핑 (`_is_quota_error`) |

### 4-3. 설계 시험과 그에 따른 설계 변경

**(가) 실제 실행·시험에서 발견해 고친 것**

| # | 발견한 문제 | 발견 경위 | 변경 |
|---|---|---|---|
| 1 | 판정 시간대가 12:00에서 끝나는데 종료 제한은 14:00 | 실제 `chat_cli` 실행 결과 | `effective_end`: end_time과 end_by 중 늦은 쪽까지 조회 |
| 2 | 파고 결과의 후보 스팟이 해변 날씨 Tool에 그대로 전달되지 않음(계획의 스팟 목록을 그대로 사용) | 문서 작성 중 설계 대조 | `chain_beach_args`: 파고 결과의 spot_id만 전달 (`test_nodes.py` 케이스 7) |
| 3 | Kakao 쿼터 초과(HTTP 400 + 코드 -10)가 `INVALID_INPUT`으로 분류됨 | API 정책 조사 후 코드 점검 | `RATE_LIMITED`로 매핑 (`test_places_quota.py`) |
| 4 | 저장 시각이 `+09:00` 그대로 화면에 노출 | 화면 확인 | 프론트 `fmtTime`으로 표시 정리 |
| 5 | 스팟의 해변 번호가 잘못 대응(`beach_num=1`이 을왕리) | 기상청 API 호출 확인 | 서핑 스팟별 번호를 다시 확인해 `spots.py` 수정 |

**(나) 설계 단계에서 위험을 미리 막은 것** (실제로 문제가 터진 기록은 아니며, 설계 선택의 이유입니다)

| # | 예상한 위험 | 설계 선택 |
|---|---|---|
| 1 | LLM이 답변까지 쓰면 숫자가 바뀔 수 있음 | respond는 규칙 기반, LLM은 analyze만 사용 |
| 2 | LLM이 말하지 않은 시각·날짜를 짐작해 채울 수 있음 | 프롬프트에 “말한 것만 채움” 명시 + 코드 검증, Tool에는 사용자가 말한 시각만 전달 |
| 3 | 후속 요청(“포항은?”)마다 조건을 다시 물으면 불편함 | 조건 병합(바뀐 항목만 갱신)과 최근 6턴 보관 |
